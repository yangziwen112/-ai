# 项目叙事与整体规划

这份文档统一项目的表达方式和推进节奏，避免 README、管理中心、AI 回复和采集摘要各说各话。

## 一、项目应该如何被理解

对外介绍时，始终使用这条主线：

> 民大通以中央民族大学为真实校园场景，解决信息分散、时间不清、来源难核验和行动难落地的问题；它通过采集、标准化和 AI 助手，把校园信息变成学生可以直接使用的事项。

不要把项目描述成“万能聊天机器人”“全网爬虫”或“简单信息展示页”。这些说法会夸大能力，也无法体现项目真正的价值。

## 二、统一语言风格

### 面向用户

使用短句、明确动作和具体时间。先给结论，再给来源，最后给下一步。避免“经智能分析”“为您赋能”等空泛表达。

推荐：

> 报名截止时间是 X 月 X 日。信息来自某官方页面。建议先确认报名批次，再打开原文提交材料。

不推荐：

> 根据大数据分析，您可以抓住这次宝贵机会。

### 面向开发者

说明输入、输出、失败条件和安全边界。每个模块都要能回答“它依赖什么、出了问题怎么办、会不会泄露数据”。

### 面向 GitHub 读者

采用“问题 → 方法 → 实现 → 验证 → 下一步”的结构。先让读者理解为什么做，再展示代码如何解决问题；不要把安装命令和内部排错日志放在项目故事之前。

### 面向采集摘要

固定使用：

```text
对象｜时间/截止｜地点｜下一步
```

缺失字段不猜测，直接省略或写“需打开原文确认”。

## 三、产品推进顺序

### 阶段 0：可信底座

- 固定官方来源目录和采集分组；
- 统一 `contents` 字段；
- 保留原文链接、发布时间和抓取日志；
- 清理虚构内容和临时图片；
- 建立 JavaScript、RAG、采集器和 Skill 测试。

完成标准：用户看到的每条官方信息都能回到来源，采集失败不会生成替代假数据。

### 阶段 1：校园事项化

- 增加截止时间、开始时间、地点、对象和行动项；
- 在首页提供“即将截止、与你相关、刚刚更新”；
- 对同一通知的更新建立版本关系；
- 让 AI 输出“是否还能办理”和“下一步做什么”。

完成标准：用户不打开原文，也能先知道这条信息是否与自己有关；需要办理时可以一键回到原文。

### 阶段 2：个性化提醒

- 让用户订阅学院、校区、考试和竞赛标签；
- 生成每周校园简报；
- 只给受影响用户发送变化提醒；
- 支持用户确认后加入日历。

完成标准：提醒减少遗漏，而不是增加打扰；用户可以解释每一条提醒为什么出现。

### 阶段 3：校园知识网络

- 连接学院、部门、校区、赛事、考试和学生组织；
- 支持“和我专业相关”“离我最近”“这周还能报名吗”等问题；
- 识别重复通知、冲突时间和缺少原文的内容。

完成标准：AI 能够基于关系和时间回答问题，而不是只做关键词匹配。

### 阶段 4：多模态与可迁移

- 理解通知截图、课程表、考场安排和二手物品图片；
- 将授权的视频内容转为可搜索文字；
- 把来源适配、字段标准和权限规则抽象为学校配置。

完成标准：更换学校来源时无需重写核心业务，且不复制任何学校的私有数据。

## 四、项目质量指标

不要只看“抓了多少条”“模型回答多长”，建议持续观察：

- 从官方发布到平台可见的平均延迟；
- 资讯含来源和明确时间的比例；
- 重复、过期和低相关内容的拦截比例；
- 用户找到行动项所需的步骤数；
- AI 回答的证据覆盖率和审核通过率；
- 用户主动关闭提醒或反馈错误的比例。

## 五、对外文案模板

### 项目简介

> 我做了一个面向中央民族大学学生的校园信息聚合小程序。它不只是收集通知，还会核验来源、提取时间和行动项，并通过 AI 助手帮助用户快速判断“这件事和我有什么关系”。

### 技术亮点

> 项目使用微信小程序和云函数承载业务，用来源目录和标准化字段治理校园资讯，再用 LangGraph 编排意图识别、检索、生成、审核与反思流程。系统优先保证来源和权限边界，而不是追求无依据的长回答。

### 项目边界

> 平台不会把用户私密数据直接交给模型，也不会在采集失败时用虚构内容填充页面。所有考试、竞赛和政策信息都应回到官方原文确认。

## 六、语言维护清单

- 新增页面前，先写清它解决的一个用户问题；
- 新增采集器前，先登记来源、分组、时间窗口和失败表现；
- 新增 AI 工具前，先定义允许读取的字段和禁止返回的字段；
- 新增文档前，先判断它属于产品、技术、部署还是研究，避免根目录继续堆放临时 Markdown；
- 每次发布前检查标题、摘要、按钮文案和错误提示是否使用同一套词语。
