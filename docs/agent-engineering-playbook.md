# 校园 Agent 工程实践手册

这份手册把项目中的实现提炼成一套可以迁移到其他校园业务的 Agent 方法。它不把 Agent 描述成一个神秘的“会聊天程序”，而是把它拆成可观察、可测试、可拒绝的工程组件。

## 1. 先定义任务，再选择模型

每个用户问题先经过情境识别和意图路由：查公开资讯、查当前时间、联网搜索、平台帮助、账号操作或安全拒答。路由结果决定可用工具和可见数据，而不是让模型先自由阅读数据库。

## 2. 用状态图表达工作流

项目使用 STAR：

```text
Situation  识别情境与风险
Task       判断意图与工具
Action     查询证据、调用工具、生成草稿
Review     审核来源、时间、隐私和表达
```

每个阶段都写入 trace。出现问题时，可以知道是路由错误、检索为空、模型失败还是审核拒绝，而不是只看到一句“AI 调用失败”。

## 3. 工具是权限边界，不是函数列表

工具调用前要回答三个问题：

1. 用户是否有权看到这类数据？
2. 这个工具是否真的能解决当前意图？
3. 工具返回的字段是否需要再次做公开投影？

校园数据库对 AI 只返回公开资讯字段；个人历史、私信、收藏明细和管理员数据不能因为“模型想知道”就自动开放。

## 4. 证据优先，回答其次

回答生成前先整理证据：来源、标题、发布时间、截止时间、地点、适用对象和下一步。证据不足时，回答必须承认不确定性。对精确日期、考试地点和报名资格，宁可引导用户查看原文，也不凭语言流畅度制造确定性。

## 5. 质量评测要贴近真实任务

项目当前检查四类质量：

- 证据：回答是否有可见来源；
- 安全：是否泄露隐私或给出无依据日期；
- 表达：是否简短、直接、不重复问题；
- 行动：是否告诉用户下一步做什么。

下一阶段可以加入人工标注集、来源新鲜度、回答事实一致性和用户点击原文后的反馈，形成从离线测试到线上观测的闭环。

## 6. 适合继续研究的方向

- 用结构化输出替代自由文本意图分类；
- 用混合检索同时处理关键词、时间和语义相似度；
- 用事件版本链处理通知更新，而不是把新旧通知并列展示；
- 用小模型完成路由、分类和脱敏，用大模型完成复杂解释；
- 用人工审核队列承接低置信度内容；
- 用用户授权的事项记忆替代无边界的聊天记忆。

这套方法的目标不是让 Agent 看起来更复杂，而是让它在真实校园环境中更少误导、更容易维护，也更容易被另一个开发者接手。
