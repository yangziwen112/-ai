# 从校园资讯到 AI 助手：面向学习者的校园信息化实践

> 把散落在学校官网、学院通知、竞赛平台、考试考证页面和校园墙里的信息，汇聚成一个真正懂校园、能持续更新的个人信息助手。

这是一个以中央民族大学校园场景为背景的完整学习案例。它试图解决一个每天都会遇到的问题：校园信息分散在不同官网、学院栏目、通知群和平台中，学生往往需要反复搜索、比对和确认。案例把官方通知、竞赛与实践、考试考证、校园动态、二手书和 AI 助手放在同一套小程序体验中，让信息从“到处寻找”变成“集中获取、按需理解”。教资只是“考试考证”中的一个分类，不是平台主线。

这里的“聚合”并不等于把所有内容无差别地堆在一起。项目更关心的是信息进入系统之后是否还能保持身份：官方通知必须能回到原文，学生发布必须标明它是校园交流，二手书必须有适合交易的结构化规格，模型生成的解释必须和可见证据对应。只有保留这些边界，平台才不会从“信息碎片化”滑向“新的信息噪音”。

## 功能分层

- 官方资讯：只展示可核验来源，保留发布时间、来源和行动项。
- 校园动态：学生发布文字、标签和图片；二手书使用独立规格字段。
- AI 助手：先识别意图，再查时间、官方资讯或受控数据，最后审核答案。
- 管理中心：按来源运行独立采集任务，查看成功、过滤和失败原因。
- 内容处理：对用户有权使用的公开视频进行详情整理、转写和摘要。

## AI 工作流

工作流采用“识别—路由—检索—生成—审核”的状态图。时间使用服务器时间，数据库只返回公开投影，用户私有数据必须经过身份校验。答案尽量短，先给结论，再给来源和下一步。

在交互上，AI 助手不要求用户学习固定指令。用户可以像和同学聊天一样提问，但系统内部会把问题拆成更明确的任务：是查一条通知、比较两个时间、寻找适合自己的比赛，还是需要解释一张上传的图片。只有真正需要的工具才会被调用，长篇原文会先压缩成与问题相关的证据，避免把无关内容和历史对话全部交给模型。

当来源不足或时间无法确认时，助手会主动降低语气强度，告诉用户“目前能确认到什么、还缺什么、应该去哪里核对”。这种克制比强行给出一个看似完整的答案更重要，因为校园通知中的一个日期或地点错误，可能直接影响报名和考试安排。

## 真实性与隐私

采集器失败时显示失败，不用演示数据兜底。第三方服务的具体地址、密钥和内部 Token 只在云函数环境变量中配置；公开仓库只保留变量名和脱敏示例。发布前执行假链接扫描和密钥扫描。

## 本地开发

1. 安装微信开发者工具和 Node.js LTS。
2. 分别安装 `api`、`rag`、`crawler` 云函数依赖。
3. 在云端配置模型、搜索、内部通信和采集器环境变量。
4. 运行语法检查、工作流测试，再在开发者工具中验证登录、游客额度、聊天会话、采集器和二手书发布。

不要把云数据库导出文件、用户图片、视频缓存或任何访问凭证提交到 GitHub。

## 学习路线与练习顺序

建议按“先能运行，再能解释，最后能扩展”的顺序阅读：

1. 先运行小程序，观察首页、校园动态、AI 助手和二手书发布的完整链路。
2. 阅读 `cloudfunctions/crawler/lib/source-catalog.js`，理解来源目录、字段标准和失败处理。
3. 阅读 `cloudfunctions/rag/lib/workflow.js`，对照 STAR 节点理解情境识别、意图路由、检索、生成和审核。
4. 修改一个低风险业务 Skill，例如新增一个竞赛来源，并为它补充测试。
5. 最后再修改 UI 或模型提示词，用测试验证“更短”是否仍然“更准确”。

每一步都对应一个可验证的问题：数据从哪里来、为什么被保留、模型能看到什么、答案为什么被拒绝，以及用户下一步能做什么。这样学习者不需要先掌握所有框架，也能从一个真实业务逐层理解 Agent 系统。

## 展示项目时如何讲清楚价值

推荐使用“问题—方法—证据—边界”的结构：先说明校园信息为什么碎片化，再展示来源治理和 Agent 编排如何解决问题，接着用测试和运行日志证明流程可验证，最后明确隐私、时效和人工审核边界。比起堆叠页面数量，这种讲法更容易让读者理解哪些设计可以迁移到自己的项目。
