# 相关项目研究与高级实践

本页记录对公开 GitHub 项目的定向研究，只提炼工程方法，不复制代码、数据或密钥。研究重点是如何把一个个人 AI 小程序做得更可靠、更省 Token、更容易持续维护。

仓库热度只作为“值得阅读”的信号，不代表代码可以直接照搬。下表中的 Star 数量是 2026-08-22 通过 GitHub 公开仓库信息核验时的近似值，之后会自然变化；真正被本项目吸收的是状态设计、评测方法和工程边界。

这些项目共同说明了一件事：真正可维护的 Agent 不是“多放几个模型”，而是把状态、工具、权限、证据、评测和失败路径写成可以被检查的系统。

## 已吸收的高级知识

### 1. 证据评分而不是“检索即可信”

检索结果要经过来源可信度、发布时间、内容相关性和字段完整性评分。低分内容可以作为候选，但不能直接支撑确定性回答。

### 2. 自校正要有预算

反思不是无限循环。当前工作流最多进行一次修订；未来可以按照风险等级分配预算：普通闲聊不重试，时间和考试问题需要证据复核，涉及隐私或权限时直接拒答。

### 3. 上下文工程优先于盲目扩大模型

对话历史、采集正文和工具结果都先压缩、去重和排序，再交给模型。这样能减少费用、缩短响应时间，也降低模型被无关内容带偏的概率。

### 4. 评测必须贴近校园任务

不能只测试“回答像不像人”。应建立校园任务集：截止时间查询、考场地点、竞赛报名、学院通知、二手书规格、登录权限和不确定问题，并检查答案是否给出来源、时间和下一步。

### 5. 采集系统需要礼貌和可恢复

采集器应遵守站点规则、限制并发、缓存成功页面、记录失败原因，并支持从上次断点继续。解析规则和 AI 摘要规则分离，单个来源变化不应拖垮整个采集任务。

### 6. 质量分数必须能解释

本项目新增的回答质量评估不是“模型自我打分”，而是可重复的本地规则：证据是否存在、是否承认不确定性、是否给出下一步、是否过长、是否出现没有依据的精确日期。分数会写入工作流 trace，便于后续构建回归面板和人工抽检队列。

### 7. 并行工具优先于串行等待

公开数据库、联网搜索和时间读取互不依赖时可以并行执行；只有在意图路由后才启动需要的工具。这样既减少延迟，也能让“查时间”和“查资讯”在一次对话中形成可解释的工具轨迹。

## 下一步工程动作

1. 增加校园问答回归样例和最低质量阈值。
2. 为每条资讯增加 `freshnessScore`、`evidenceScore` 和 `revisionOf` 字段。
3. 在管理员中心增加采集延迟、过滤率、失败率和重复率趋势。
4. 对长对话采用摘要记忆，对检索正文采用分层摘要。
5. 将“加入日历、订阅更新、查看原文”作为 AI 输出的结构化行动，而不是只返回文字。

## 前沿开发方向

### 面向事项的 Agent Memory

把“用户问过什么”升级为“用户确认过哪些校园事项”：例如关注某个学院、已经报名某项考试、等待某场比赛结果。记忆只保存用户明确授权的结构化偏好，不保存完整聊天原文；当来源发生变化时，系统只唤起受影响的事项。

### 证据图与版本链

将通知、来源、时间、地点、对象和更新版本连接成证据图。回答“这条通知是否更新过”时，系统不只检索关键词，而是沿着版本链解释哪些字段发生变化。

### 人机协同审核队列

对低证据、时间冲突、疑似过期和来源变更的内容建立人工复核队列。模型负责排序和摘要，管理员负责最终发布；这是比“让模型自动发布所有内容”更适合校园场景的落地路径。

### 小模型路由与大模型生成

意图识别、敏感词检查、时间格式化和摘要裁剪优先使用本地规则或轻量模型；只有需要复杂解释时才调用大模型。这样可以降低成本、缩短响应时间，也更容易在云函数环境中稳定运行。

### 可迁移的来源适配器

未来把学校官网、学院栏目和竞赛平台抽象成来源适配器：每个适配器只负责发现页面、解析字段和报告失败，不把具体网站逻辑散落在业务代码中。更换学校时替换配置和适配器，核心 Agent、权限和评测体系保持不变。

## 面向大学生的真实业务 Skill

项目新增三个可复用 Skill：

- `campus-teacher-cert`：教资、考研、四六级等考试节点。
- `campus-competition-tracker`：三创赛、创新创业大赛、挑战杯和校内竞赛。
- `campus-source-governance`：来源核验、去重、时效、证据评分和权限投影。

这些 Skill 是对官方来源页面的处理规则，不是虚构的活动数据。只有抓取成功且通过学生相关性筛选的内容才会进入资讯库。

研究结论：民大通真正的技术壁垒不是接入更多模型，而是把校园来源、时间、权限、内容质量和用户行动组织成一套可验证的系统。
